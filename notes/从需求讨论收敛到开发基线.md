# 从需求讨论收敛到开发基线

## 1. 先区分事实源和分析产物

开始分析前，应明确哪些文件是需求提出者提供的原始需求，哪些是研发或 AI 生成的分析、设计和讨论记录。

后续每个结论都应能回答：

- 这是原始需求明确规定的吗？
- 这是从现网行为观察到的吗？
- 这是研发为了可实现性补充的设计吗？
- 还是尚未确认的合理假设？

如果不区分来源，AI 很容易把自己提出的抽象重新当作需求依据，形成循环论证。

## 2. 把问题压缩到“无法安全脑补”的决策

需求评审不应追求问题数量。大量边缘问题通常可以通过行业惯例、统一技术约束或低风险默认值解决。

真正需要需求提出者回答的，是答案不同会直接改变以下内容的问题：

- 业务对象和唯一性；
- 数据完整快照还是局部变更；
- 删除、停用和生效语义；
- 审批后的覆盖、合并或冲突行为；
- 不可逆的数据保留策略。

例如，与其连续追问“正常状态为何存在、删除记录存哪里、未出现的旧明细怎么办”，不如压缩为一个根问题：

> 本次提交表达的是目标完整状态，还是相对当前状态的变更集合？

这个答案确定后，多个派生问题可以由设计自然回答。

## 3. 低代码表单不是领域模型

迁移低代码系统时，最常见的错误是把页面、子表、状态列和操作按钮原样翻译成数据库表。

需要反向识别：

- 哪些是真正长期存在的业务实体；
- 哪些只是某次审批使用的单据；
- 哪些只是界面为了展示差异而产生的临时状态；
- 哪些字段只是低代码平台为了级联、恢复或查询而留下的实现痕迹。

如果业务始终围绕一个组合整体提交、审批和生效，这个组合通常应该成为显式聚合，而不是继续把组级属性重复在每一条明细上。

## 4. 一个字段只表达一种业务事实

当一个字段需要通过来源标记、特殊值或复杂恢复规则才能解释时，通常意味着它承担了多个职责。

典型反例：一个“停用”字段同时表达人工停用和上级对象停用。随后系统不得不增加“停用来源”，并编写复杂的级联写入和恢复逻辑。

更稳定的表达是分别保存独立事实：

```text
实际不可用 = 人工停用 OR 上级对象停用
```

上级状态不应覆盖下级的人工意图。最终状态可以查询计算；如因性能需要物化，也应保持原始事实彼此独立。

同样需要警惕：

- 把单据版本和数据版本放在一个字段里；
- 把最近生效来源和历史版本归属放在一组来源字段里；
- 把本次变更类型命名为实体长期状态。

## 5. 快照应保存在需要历史语义的地方

名称、规格等主数据快照适合出现在不可变的历史单据中，因为历史单据需要还原审批当时看到的内容。

只保存当前状态的业务表通常只需保存主数据标识，展示时关联当前主数据。否则会出现两套都看似正确的数据：主数据已经改名，当前业务表仍显示旧名称。

可按以下原则判断：

| 数据位置 | 名称快照建议 |
| --- | --- |
| 已审批历史单据 | 保存，保证历史可还原 |
| 当前状态表 | 通常不保存，关联主数据展示 |
| 对外法律凭证、结算凭证 | 保存，按发生时事实冻结 |
| 纯派生值 | 仅在有性能或留痕需要时冗余，并由服务端统一计算 |

## 6. 两种修改单必须共享并发基准

当“完整重报”和“局部批量修改”都能更新同一份当前数据时，不能各自维护互不相干的版本规则。

推荐为目标聚合维护统一的数据修订号：

1. 创建单据时记录基准修订号；
2. 任意一种单据生效后统一递增；
3. 审批生效前再次比较；
4. 基准已经变化时拒绝静默覆盖，要求重新生成或显式合并。

单据自己的流水版本仍可保留，但不能替代数据修订号。

## 7. 业务先行、流程后挂，但要预留边界

复杂业务和流程平台增强可以分阶段实施：

1. 先完成业务 CRUD、计算、校验和生效闭环；
2. 固定表单字段标识与后端更新边界；
3. 再实现流程节点的字段可见、可编辑、必填能力；
4. 最后完成审批表单与业务生效的端到端联调。

第一阶段可以通过直通模式验证业务，但不能视为完整需求交付。业务代码至少应提前具备：

- 稳定的字段编码；
- 按字段白名单更新的能力；
- 审批中修改不直接触发生效；
- 直通与正式审批共用同一生效服务。

## 8. 定稿后收敛文档，而不是抹掉历史

需求接近稳定时，应把讨论过程收敛为职责清楚的当前文档。结构不必固定成统一模板；对于采用 ER 图进行需求分析、再进入软件设计的工作方式，可以使用：

| 文档 | 内容 |
| --- | --- |
| 需求分析 | 术语、业务对象、概念 ER 图、业务规则和少量当前未决 |
| 软件设计说明 | 逻辑 ER 图、表结构、流程、接口、状态、并发、迁移和测试 |
| 决策记录（可选） | 正文无法自然说明的关键取舍及不可逆影响 |

被推翻的方案、往返讨论和临时默认值不应继续出现在开发入口文档中，但可以移入只读归档，避免以后无法解释关键决策的来源。

正式文档首先服务人的理解，而不是保留分析过程。整理时应优先保留归纳后的业务关系和执行规则，并使用 Mermaid 承载适合视觉表达的内容：

- 概念 ER 图表达业务对象及关系；
- 流程图表达操作、审批和生效路径；
- 状态图表达状态转换与守卫；
- 时序图表达跨模块调用和回写顺序。

图中已经清楚表达的内容，不应再用长段文字重复。正文只补充图无法承载的约束、例外和设计理由。

## 9. “可以开发”的最低判断标准

进入开发不要求所有细节都由产品逐项确认，但至少应满足：

- 核心业务对象与唯一键明确；
- 完整状态和变更集合的语义明确；
- 新增、修改、删除、停用和审批生效规则唯一；
- 多入口修改同一数据时有冲突处理方案；
- 未决项不会改变表结构或核心算法；
- 开发人员只读基线文档就能得到唯一实现口径。

其余低风险细节可以由研发采用统一默认方案，并在设计基线中明确记录。
