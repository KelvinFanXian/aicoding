# Standardize Project Docs

为今后新建的项目文档区域统一规定编号、事实归属和读者入口。规范管**怎样记录和引用**，不预设业务模块、目录名、文件序号或实施阶段的固定文件套件。开始写入前先找项目现有规则；存量格式按兼容规则处理，新事项遵循本规范。

## 先分清内容的身份

| 内容 | 应放的位置 | 是否发正式编号 |
| --- | --- | --- |
| 来源材料、原型观察、走查证据 | 来源或分析记录；标明出处与观察时点 | 不因出现一行就发号 |
| 待定问题、关键决策、术语或原型整改、缺陷 | 对应类别的唯一登记处 | 需要跨文档追踪时发号 |
| 当前有效的需求与设计 | 当前基线；只写已确认口径与必要边界 | 只引用相关事项号，不重建台账 |
| 实施、测试、人工验收 | 执行记录、步骤、预期和证据 | 正式问题回登记处，本处引用编号与状态 |
| 对外确认工作件 | 可独立转发、让对方回答的材料 | 形成内部正式事项后回写登记处 |
| 旧方案和讨论过程 | 标明冻结时间及后继入口的归档 | 旧号可查，不再更新当前状态 |

一项事实只有一个当前权威位置。导航、黑板和汇总可以显示状态，但要指向登记处，不能各自维护另一份可独立修改的结论或统计。建立新文档前明确它服务谁、何时阅读、与现有文档的职责差别；答不清时沿用现有文档。

## 正式编号：封闭格式与释义

只为需要跨文档引用、持续更新状态或长期追溯的事项发号。步骤、轮次、表格行号和一次性观察用数字或标题；脚本、接口等资产引用时带类型及可定位名称，不混入事项编号。

编号统一写作 `<作用域码>:<类别码><两位起始序号>`，例如 `G:Q01`、`G:DR01`、`G:B02`。`G` 来自 Global，表示全局事项；没有细分范围时也用 `G`，不省略作用域。确需按不同范围分别发号时，先在规则中登记范围码、完整名称及边界；不预设模块码表。每个“作用域 × 类别”从 `01` 递增，已发号不复用、不重排。

| 类别码 | 英文出处 | 何时使用 | 状态或处理 |
| --- | --- | --- | --- |
| `Q` | Question | 答案尚未确定、会影响后续判断的问题 | 待定 → 已定；普通结论回写行内。影响数据结构或不可逆行为的关键定案另记 `DR`，原 `Q` 保留关联 |
| `DR` | Decision Record | 已定案、未来容易被误改的重要结论及理由 | 定案即生；不可逆标 `⚠️`，与正式需求有差异标 `🔀` 并解释。被新决策取代时保留旧号和后继链接 |
| `T` | Terminology | 需要统一的名称或术语 | 待改 → 已改 |
| `P` | Prototype | 已确认的原型整改项 | 待修 → 已修／明确以已确认正文为准 |
| `B` | Bug | 预期明确且已核实的缺陷 | 待修 → 已修待验证 → 已验证；预期未定时先记 `Q`，不把争议直接定为缺陷 |

没有原型的场景不发 `P` 号；普通结论不必都升级为 `DR`。正文首次引用或面向新读者时写“待定问题 `G:Q01`”“缺陷 `G:B02`”，并链接登记处。读者不应靠猜字母理解编号。

类别码限于上表。不得因为发现清单、页面走查或复测轮次而临时造 `F1`、`W1`、`R1` 等新前缀。确实无法归类时，先说明现有类别为何不够、拟新增代码的完整含义、唯一登记处、同号风险与旧号迁移方式；修订本规范后才能发号。

首次发号前，规范入口至少登记两张映射：**作用域码 → 完整名称与边界**，以及 **作用域 × 类别 → 唯一登记处与当前最大序号**。多个类别可以共用一份文档，但每个组合只能有一个权威位置。事项行至少能查到编号、简明标题、来源、当前状态、结论或处理结果、关联编号与最后更新时点；`DR` 补定案理由，`B` 补验证证据。没有登记处就先建登记处，不在引用文档里代发号。

## 登记、引用与流转

1. **先登记，后引用。** 每个正式编号只有一个登记处负责定义、状态、结论和后继关系。新事项先核对是否已有编号覆盖，再发下一号。其他文档保留必要摘要和链接，不自行造号或单独改状态。
2. **来源号不等于内部号。** 外部测试单、产品反馈或旧系统的编号只作来源映射；先核实真实性、预期和重复项，再决定是否登记内部 `Q` 或 `B`。重复反馈指向原号，不再发一个相同问题的新号。
3. **观察与正式缺陷分流。** 当轮可处理的内部观察在当轮记录中写明发现、调整和验证证据；未处理完不能写“已验证”。需要持续跨文档追踪时进入正式登记处。外部反馈与内部自查保留来源区别，但同一问题不建立两套互相竞争的状态。
4. **迁移不丢身份。** 分析期的开放事项进入新登记处时，保留原号、状态和旧入口；已定问题把结论回写当前基线，重要决策另记 `DR` 并相互链接。验收清单回填编号和状态，问题正文仍在登记处。

## 从分析材料到当前基线

分析记录允许保存来源、疑点和推演；进入开发基线前，先解决会改变业务对象、核心流程或不可逆处理的关键问题。基线只呈现当前有效的需求与设计；旧方案、反复讨论和临时观察退出正文，归档文件注明冻结时间及当前入口。仍开放的问题留在活动登记处，不能因分析文件归档而失踪。

面向外部人员的工作件用业务语言说明问题、选项和所需回答，避免内部编号及实现路径妨碍确认。得到答复后更新登记处和受影响的基线；外部工作件不承担内部状态户口。

修改历史只记录会改变读者判断的实质变化：新增或改定规则、关键决策、状态推进等。纯排版、措辞和多轮编辑过程不逐条占行。项目有文档检查脚本时运行它，并核对链接、表格、时间顺序及意外暴露的本机路径或凭据。

## 旧文档兼容

既有不同格式的编号冻结并继续可查，不为形式统一批量改号；新事项使用本规范。引入时先检查旧号与新号冲突、登记处位置和引用入口。若项目已有另一套正在使用的编号规则，先明确迁移与读者影响，不静默改写存量文档。
