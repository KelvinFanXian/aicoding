# Govern Project Docs

为需要长期协作的项目文档建立可追溯的写入规则。先核对项目现有约定和真实文档，再决定是否需要编号体系、台账或阶段目录；不要把另一项目的码表、文件名和阶段模板直接移植过来。

## 先判断是否需要治理

关键问题是：**读者能否从一个确定的位置找到事项当前状态和有效结论？**

- 只有少量独立文档时，直接在正文维护结论即可；不为形式统一引入编号和台账。
- 同一问题跨需求、设计、测试或验收文档流转，且需要稳定引用和状态追踪时，才建立正式编号与唯一登记处。
- 已有项目规范时先沿用。若拟议规则会改变现有编号、归档或阅读入口，明确迁移影响，取得项目负责人的决定后再执行。

例如，走查文档中的“步骤 1”和表格第 3 行是局部顺序；跨文档追踪的缺陷才需要正式编号。不能先在走查记录里造一个看似正式的号，再让台账追认。

## 编号与登记处

项目确需正式编号时，先明确四件事：适用范围、事项类别、唯一登记处、编号的稳定性。编号格式由项目确定，不预设固定前缀或类别集合。

1. 写入前判断是局部顺序、资产编号，还是需跨文档追踪的事项。局部顺序用普通数字；脚本、接口等资产引用时带类型和可定位路径。
2. 正式事项先在其登记处建档，再由其他文档引用。登记处负责定义、状态和结论；引用处只写读者当下需要的摘要及链接，不另维护一份状态。
3. 已发编号保持稳定；关闭、定案和归档只改变状态或所在文档，不复用编号。迁移登记处时保留可追溯的旧入口或跳转。
4. 新类别或新前缀若不在现有规范内，先判断普通标题、局部序号或既有类别是否足够。确需扩展时，说明原体系为何不够、唯一登记处、冲突与存量迁移，再修改规范和发号。

历史编号可以冻结保留引用，不必为了表面一致批量重排；冻结后同类新事项按现行规则登记。

## 文档职责与阶段流转

按读者任务分配文档职责，而非按每个阶段机械生成全套文件。常见分工是：分析材料保存证据和待定问题；当前基线保存可执行的需求与设计；决策记录保留未来容易被误改的重要理由；实施与验证记录执行结果；测试或验收材料保存步骤、预期和证据。一个事实只在一处维护当前版本。

进入开发基线前，确认会改变关键模型、流程或不可逆行为的问题已定案。收敛时把结论回写当前基线，撤出互相矛盾的旧方案；讨论过程移入归档并标明其非当前依据。实施后的缺陷按已有问题登记机制处理，验收清单只引用编号和状态，不再复制问题正文。

对外沟通件与内部执行记录分开：前者应能独立阅读，避免内部编号和实现细节妨碍业务确认；外部确认若形成正式问题或决策，回写对应登记处和基线。

阶段边界取决于项目实际工作方式。分析与实施并行、或文档规模较小时，可以合并文件；只要当前权威位置、历史入口和状态责任仍清楚即可。

## 写入前后核对

写入前确认适用的项目规范、读者、文档职责，以及这次内容应进入正文、登记处、执行记录还是归档。写入后核对编号先登记后引用、同一事实是否出现两处可独立修改的当前版本、旧结论是否仍冒充有效依据，以及链接是否指向真实位置。

修改历史记录会改变读者判断的实质变化；纯措辞、排版和临时编辑过程不必逐条占行。项目已有校验脚本时运行它，并检查表格、链接及意外泄露的本机路径或凭据。
