# 用测试工程师的视角做交测前自查

先问：**本轮改动可能出现哪种看起来能用、但实际错误的实现？什么最小样本能让它与正确实现得到不同结果？** 这比继续增加测试项更有价值。历史缺陷只帮助想出可能的错法；预期须从当前有效需求、产品确认或接口契约独立确定，不能照着实现倒推。用户只要测试方向时，交付方向与样本，不擅自操作系统。

例如明细“重新带入”：只测首次成功，无法识别“第二次只追加、不替换”。若已确认规则是替换，就先宽后窄带入两次，保存重开后只应有窄条件结果；若替换口径未确认，先列为待确认，不判 Bug。

```mermaid
flowchart LR
    A[本轮改动] --> B[一种可能蒙混过关的错法]
    B --> C[让对错结果分叉的最小样本]
    R[当前有效规则] --> D[独立确定预期]
    C --> E[观察最终业务结果]
    D --> E
    E --> F[按证据判定结果]
```

## 优先给 Agent 的测试方向

下表只用于启发可能的错法，不是必测清单。优先选择能指出具体错法、构造区分样本且有独立预期的方向；如果正确和错误实现都会通过该用例，换样本或不列为重点。

| 变化类型 | 测试工程师常用的切入方式 |
| --- | --- |
| 输入或业务约束 | 测空、默认值、零、负数、精度、上限及上限外一格；有关联字段时只填一边，明细测零行/一行/多行。观察控件是否偷偷钳制或截断，以及服务端是否同口径拦截、给出可理解的错误。先确认零、空、默认值在该场景的真实语义。 |
| 自动带出、计算与联动 | 改一个源值后看派生值；再切换来源、修改已有行、改回原值、保存后重开。用非整除、不同值样本区分计算、精度和百分比展示；不要只看表单内即时显示。 |
| 状态与反向动作 | 走保存、提交、审批、退回、作废或反审核中与改动相关的路径；核对必填原因、按钮可用范围、状态、汇总回写和审计留痕。提示文案正确不证明最终数据正确，正向通过也不证明反向已还原。 |
| 字段与页面入口 | 对同一概念检查列表、选择器、新增/编辑、详情、校验提示和旧数据；区分“同名不同义”字段。检查功能入口真实可见可点，而非 DOM 中存在；检查表单默认值会不会令某个异常用例在 UI 上不可构造。 |

观察按风险延伸到**控件实际值 → 请求/响应 → 保存后读取 → 受影响的下游**，不要求每个小文案都查数据库。瞬时提示先用截图、监听或请求证据复核，避免把没捕获到当作没出现。

## 结果判定

用例步骤或原型与当前确认规则冲突时，先核对预期，不照单提缺陷；场景无法从用户入口构造时，标为未覆盖或转到合适的接口层验证，不虚构一次通过。区分“功能确实错误”“用例预期过时”“产品口径未定”“证据不足”，并注明哪些断言仅部分通过。一次修复或一轮自查不能自动升级为人工已验收。

给 Agent 的简短输入可写成：

> 请按当前有效需求和本轮改动，找几种看起来能用、却可能做错的实现。每种给一个能让对错结果分叉的最小样本，说明独立的预期来源及最终要观察什么。预期未定或证据不足的，单列待确认，不当作已证实的缺陷。
