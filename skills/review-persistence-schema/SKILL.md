# 评审持久化结构

先根据已确认的业务场景和现有数据结构确定要保存的事实，再决定是否新增表或字段。上游单据、页面分区和未来可能的扩展都只是线索，不能直接等同于本地实体。

## 决定是否新增

- 对拟新增的表，确认它是否有独立身份、生命周期或必须单独保存的关系；现有对象能承载同一事实时，先说明为何不能复用。例：上游有“用料单”，但本地任务已唯一对应一张用料单且明细只随任务使用时，单独复制一个用料单头表会增加维护点；若用料单可跨任务复用或独立变更，则应重新考虑独立建模。
- 对拟新增的字段，区分当前主数据引用、历史快照和派生结果。同一当前事实只设一个权威写入位置；历史需要还原当时值时，注明冻结时点及其不随主数据更新的语义。可稳定计算的结果通常先在读取时计算，确需存储时说明历史或性能依据与更新责任。
- 对模型中仍未确认、且会改变实体身份、关系或历史处理的选择，保留为待审核设计，不提前进入 DDL 或代码。已确认部分可按阶段继续。

## 控制整改范围

收到“字段类型不合适”“约束太多”一类反馈时，先定位受影响的字段和实际规则，再修改相应部分。字符串长度要有业务上限依据；状态枚举、自由文本与长度限制分别判断。在 PostgreSQL 中，不能仅因使用 `text` 就认定字段设计错误。约束放在数据库还是业务代码，遵循项目既定口径；若改由代码保证唯一性或状态不变量，需核对所有写入入口及并发时持锁后读取的状态。

迁移的前置阻断只针对会使本次结构或数据变更不安全的条件。执行后以实际结构和关键数据核验结果；脚本已交付、有人执行或查询仍能返回行，都不足以证明迁移已生效。

输出以最小变更及其理由为主：保留、复用、删除或新增什么；依据来自已确认需求、现有代码或验证的哪一部分；哪些仍是待确认假设。后来的业务决策改变，不反推旧设计必然错误。
