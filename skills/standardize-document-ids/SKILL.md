# Standardize Document IDs

本 Skill 统一规定今后新建跨文档事项的编号。目标是稳定引用、读者看得懂、状态有唯一登记处。新场景按下列格式和固定类别码发号；既有旧号按文末兼容规则处理，不搬用任何项目的模块码表。

## 先决定要不要编号

只有需要跨文档引用、持续更新状态或长期追溯的事项，才发正式编号。步骤、轮次、表格行号和一次性观察使用普通数字或标题。脚本、接口、菜单等资产已有自己的标识，引用时写明资产类型和可定位名称，不把它们混进事项编号。

例如“步骤 1：提交申请”不需要事项号；若一个缺陷会同时出现在测试记录和修复台账，才按下表发 `B` 号。

## 固定类别码与状态

| 类别码 | 英文出处 | 含义 | 生命周期 |
| --- | --- | --- | --- |
| `Q` | Question | 待定问题，需要明确业务或技术结论 | 待定 → 已定；结论回写登记处。影响数据结构或不可逆行为的关键定案另记 `DR`，原 `Q` 保留关联 |
| `DR` | Decision Record | 已定案的重要决策及理由 | 定案即生，持续有效；不可逆决策标 `⚠️`，与正式需求存在差异时标 `🔀` 并说明差异 |
| `T` | Terminology | 名称或术语统一项 | 待改 → 已改 |
| `P` | Prototype | 原型整改项 | 待修 → 已修／以已确认的正文为准 |
| `B` | Bug | 缺陷，不用于尚未定案的需求 | 待修 → 已修待验证 → 已验证 |

`Q` 是待定问题，`DR` 是已定案的关键结论；不要把每个普通问题都升级成决策记录。没有原型的项目不发 `P` 号，也不为了凑齐五类而建空台账。

## 编号格式与可读性

正式编号统一写作 `<作用域码>:<类别码><两位起始序号>`，例如 `G:Q01`、`G:DR01`、`G:B02`。`G` 来自 Global，用于全局事项；新场景没有细分作用域时也用 `G`，不得省略作用域。确需在不同范围分别发号时，先登记该范围的作用域码、完整名称和适用边界，再发号；不预设任何模块清单。每个“作用域 × 类别”的序号从 `01` 递增，不复用、不重排。

类别码只用上表五种。不能因为走查、验收或某份文档需要局部行号，就临时创造 `F1`、`W1`、`R1` 等看似正式的新前缀。确实无法归入五类的跨文档事项，先说明现有类别为何不够、拟新增代码的含义与登记处、旧号如何保持可查；更新规范后才能发号。

正文面向不熟悉码表的读者时，首次引用写成“待定问题 `G:Q01`”或“缺陷 `G:B02`”，并给出登记处链接。读者应能从引用处或一个清晰的规范入口回答“代码是什么意思、去哪看当前状态”。

## 发号与引用

每个正式编号只在一个登记处定义和更新状态。先登记，再在需求、设计、测试等文档引用；引用处可以保留必要摘要和链接，但不能另维护一份独立状态。编号发出后不复用、不重排，关闭或定案只改状态。登记处迁移时保留可追溯入口。

已有不合新规范的编号冻结并继续引用，不为形式统一批量改号；新事项一律按本规范发号。引入本规范时先核对旧号与新号是否冲突，保留旧号查询入口。以后若确需改变类别或格式，先修订本规范并明确迁移方式，再按新规则发号；不得在具体文档中自行变通。
