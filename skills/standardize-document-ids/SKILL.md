# Standardize Document IDs

让跨文档事项能够稳定引用，同时让第一次读到编号的人知道它指什么。先检查项目已有编号约定、存量引用和登记位置；不要直接搬用别的项目的前缀、类别或模块码。

## 先决定要不要编号

只有需要跨文档引用、持续更新状态或长期追溯的事项，才发正式编号。步骤、轮次、表格行号和一次性观察使用普通数字或标题。脚本、接口、菜单等资产已有自己的标识，引用时写明资产类型和可定位名称，不把它们混进事项编号。

例如“步骤 1：提交申请”不需要 `S01`；若一个缺陷会同时出现在测试记录和修复台账，才需要稳定编号。

## 让编号可读

- 项目尚无约定时，默认用“类别-两位起始序号”，例如 `缺陷-01`、`决策-02`；同类序号递增，不因关闭而回收。只有同一类别在多个范围内分别发号、会产生重号时，才增加可读的范围前缀。已有稳定格式则沿用，无须为采用此默认式批量改号。
- 优先用读者熟悉的名称表达类别，例如“缺陷-01”。字母缩写只有在团队已熟悉、数量足以值得缩写，或已有大量存量引用时才使用。
- 确需缩写时，在编号规范中列明**代码、完整名称、含义、适用范围和唯一登记处**；正文首次出现或面向新读者时把类别名称与编号并写，例如“缺陷 BUG-01”。不能要求读者凭字母猜意思。
- 作用域只在不同范围会产生同号歧义时加入。范围码同样要在规范中释义；不要为了覆盖每个目录预先造一套码表。
- 类别和范围保持少而稳定。新增代码前，先核对普通标题、现有类别或不编码是否已能表达；确需新增时，说明它解决的歧义及旧引用如何保持有效，再更新规范。

读者能否只凭当前位置的文字或一个清晰入口，回答“这个号是什么、去哪看当前状态”，是检验编码是否合格的标准。若必须翻查一串陌生缩写，优先补名称或减少编码层级。

## 发号与引用

每个正式编号只在一个登记处定义和更新状态。先登记，再在需求、设计、测试等文档引用；引用处可以保留必要摘要和链接，但不能另维护一份独立状态。编号发出后不复用、不重排，关闭或定案只改状态。登记处迁移时保留可追溯入口。

已有不合新规范的编号可冻结并继续引用，不为形式统一批量改号；新事项按当前规范发号。修改编码规则时检查存量链接、同号冲突和读者入口，避免“规范更新了，文档仍查不到号”。
