# Evolve Design Docs

把文档当作帮助人建立稳定心智模型的工具，而不是保存讨论过程、AI 推理或项目进度的容器。

## 核心偏好

- 人先读懂：先给结论和整体关系，再给局部细节。
- 先建模再设计：涉及业务对象时，优先用概念 ER 澄清对象、关系、归属和生命周期，再进入表结构、接口和实现。
- 图服务于问题：优先使用 Mermaid 表达对象关系、流程、状态、时序和依赖，但不为使用 Mermaid 而画图。
- 多文档按职责拆分：不强制单一主文档；每份文档应有稳定职责和明确阅读顺序。
- 一项事实只有一个当前权威位置。其他位置使用引用或摘要，不复制完整定义。
- 正文只保留当前有效结论、必要依据和执行约束。往返讨论、被推翻方案、临时假设和实现流水退出正文。

这些是稳定偏好，不是僵化模板。根据问题性质选择合适表达；没有对象关系的问题不强行画 ER，没有复杂关系的问题不强行拆文档。

## 文档演进顺序

按认知依赖推进，不按 AI 能生成多少内容推进：

1. **来源与边界**：说明目标、范围、事实来源及不做什么。
2. **术语与概念 ER**：统一概念，识别业务对象、关系、所有权和生命周期。
3. **核心规则**：写清状态、约束、不变量、异常和最小待确认问题。
4. **逻辑设计**：形成逻辑 ER、关键字段职责、唯一性、引用关系和历史策略。
5. **行为设计**：按需要补流程图、状态图和时序图。
6. **实现契约**：补服务边界、接口、事务、权限、校验、测试和迁移方案。
7. **持续演进**：新结论直接改写当前定义，同时删除、归档或降级旧结论，避免并列保留互相冲突的版本。

前一步仍存在会改变业务对象、数据模型、核心流程或不可逆数据处理的未决问题时，不把后续猜测写成定案。

## 推荐文档职责

根据规模组合，而不是机械创建全部文件：

- **需求分析**：目标与范围、来源、术语、概念 ER、业务规则、少量当前阻塞问题。
- **软件设计**：架构边界、逻辑 ER、约束与索引、流程/状态/时序、服务与接口、事务与权限、测试与迁移。
- **决策记录**：只保存未来容易被误改、且必须保留理由的重要决策；普通结论直接进入需求或设计正文。
- **实施与验证记录**：进度、提交、分支、测试执行和临时问题单独记录，不进入设计基线。
- **来源与归档**：仅供追溯，不作为正常阅读入口。

每次新增文档前，先回答：它承担什么长期职责？读者何时进入？为什么不能写入现有文档？答不清就不要新增。

## 图与文字的分工

一张图只回答一个主问题：

- 概念 ER：业务上有什么，以及彼此如何关联。
- 逻辑 ER：系统如何保存这些对象。
- 流程图：谁在什么条件下做什么。
- 状态图：对象允许怎样变化。
- 时序图：多个组件如何按时间协作。
- 依赖图：模块边界和影响方向。

图前用一句话说明结论，图后只补图中无法表达的约束、例外和理由。避免把同一信息再完整复制为图、表格和长文三份。

## 控制问题与噪音

- 将同一根因的多个疑问压缩为一个决策问题。
- 能由明确业务规则或成熟工程惯例安全推导的，不升级为产品问题，但要标明它是设计推导而非需求原文。
- 只有答案会改变业务含义、关键模型、核心算法或不可逆行为时，才阻塞开发并请求确认。
- 问题一旦定案，更新真正受影响的章节和图；不要只在末尾追加“已决定”。
- 删除不影响读者理解与执行的段落。若删除一段后没有信息损失，它就是噪音。

正文通常不保留：

- 完整对话、推理过程和多轮拉扯；
- 已关闭问题及被淘汰方案；
- 分支、提交、工作区和阶段进度；
- 为 AI 记忆服务的编号或重复上下文；
- 来源原文、同义改写和设计结论的连续重复；
- 没有当前实施价值的未来扩展猜想。

## AI 提出优化建议

允许主动提出能降低阅读成本、减少重复或改善长期维护的优化，但不能把通用“最佳实践”静默替换成用户的稳定习惯。

提出优化时简要说明：

1. 当前具体摩擦；
2. 建议怎样调整；
3. 对阅读或维护的直接收益；
4. 代价、迁移影响或失效边界。

在用户已要求编辑的范围内，与本 Skill 核心偏好一致的小型局部优化可以一并实施并说明。新增文档、改变阅读主线、重划职责或推翻稳定偏好，先取得用户同意。

用户只要求评审或讨论时，给出判断和建议，不修改文件。

## 演进本 Skill

把本 Skill 视为可修订的偏好基线，而不是永久冻结的规范：

- 从多次真实使用中识别反复出现的阅读或维护问题；一次性项目现象不直接升级为规则。
- 新规则必须能改变后续行为，并说明适用条件或反例。
- 新证据推翻旧经验时，替换旧规则并保持内部一致，不在末尾机械追加相反意见。
- 合并重复规则，删除已经被更高层原则覆盖的细节。
- 修改前区分“用户稳定偏好”和“AI 优化建议”；未经同意，不把后者写成不可违背的偏好。

## 交付前检查

- 新读者能否不翻归档，按阅读顺序建立完整心智模型？
- 关键业务概念是否都有且只有一个当前定义？
- 概念 ER 与逻辑 ER 是否区分了业务事实和存储实现？
- 每张 Mermaid 图是否确实降低了认知成本？
- 当前结论是否已替换旧结论，而不是与旧方案并列？
- 需求、设计、决策理由和实施进度是否各归其位？
- 是否仍有未经确认的 AI 猜测被写成事实？
- 删除任一段落后若没有信息损失，是否已将其移除？
